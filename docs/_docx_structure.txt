322: [Normal] 3.4. Результати реалізації інформаційної підсистеми
323: [Normal] У результаті виконання бакалаврського проекту розроблено та апробовано прототип інформаційної підсистеми «Мобільний термінал водія» RoutePulse — клієнт-серверну систему диспетчеризації міського пасажирського транспорту з використанням мобільних платформ.
324: [Normal] 3.4.1. Основні результати розробки
325: [Normal] Реалізованими компонентами підсистеми є:
326: [List Paragraph] Android-застосунок RoutePulse (Kotlin, Jetpack Compose, Clean Architecture): 9 екранів, MVVM, JWT-авторизація, повний цикл дорожнього листа (старт → активний рейс → завершення/архівування);
327: [List Paragraph] LocationTrackingService — Foreground Service GPS-трекінгу з інтервалом 5 секунд, сумісний з Android 7.0+ (Foreground Service type location);
328: [List Paragraph] TelemetrySyncWorker — WorkManager-задача офлайн-синхронізації GPS-телеметрії батчами (до 100 точок) кожні 15 хвилин з retry-логікою;
329: [List Paragraph] Модуль реєстрації інцидентів: Android Camera API (ACTION_IMAGE_CAPTURE), кодування JPEG→Base64, геоприв'язка, версійна історія редагувань;
330: [List Paragraph] Модуль карти маршруту: OSMdroid 6, GeoJSON-трек, live-маркери активних рейсів;
331: [List Paragraph] REST API сервер (Node.js 18/Express 4/Mongoose 7): 14 захищених ендпоінтів, JWT (HS256, 8 год), bcrypt (cost 10), збереження фото у /uploads/;
332: [List Paragraph] MongoDB routepulse_db: 6 колекцій з enum-валідацією Mongoose, compound-індексами та бакетною стратегією телеметрії.
333: [Normal] 3.4.2. Результати апробації на контрольному прикладі
334: [Normal] Апробація проводилась на контрольному прикладі з використанням тестового облікового запису водія DRV-1042/password123 та seed-даних (3 маршрути з 5–8 зупинками, 5 транспортних засобів). Для автоматизованого тестування використовувались smoke-тести (npm run smoke, scripts/smoke-curl.sh), що перевіряють 14 API-ендпоінтів.
335: [Normal] Таблиця 3.5 Результати апробації підсистеми на контрольному прикладі
337: [Normal] Усі 14 API-ендпоінтів пройшли smoke-тестування успішно. UX-checklist підтвердив відповідність інтерфейсу NFR-03 (мінімальний розмір шрифту ≥16 sp, кнопок ≥64 dp). Час відповіді API на локальному сервері: авторизація — ≤50 мс, отримання маршрутів — ≤30 мс, реєстрація інциденту з фото 200 KB — ≤300 мс.
338: [Normal] 3.4.3. Оцінка практичної цінності та перспективи впровадження
339: [Normal] Порівняно з існуючими альтернативами (Wialon, Fleet Complete, AvtoGPS, проаналізованими у підрозділі 1.2), розроблена підсистема RoutePulse забезпечує такий самий ключовий функціонал (GPS-трекінг, електронний дорожній лист, реєстрація інцидентів, офлайн-режим) за значно нижчої вартості завдяки:
340: [List Paragraph] відсутності ліцензійних платежів (відкриті технології: Node.js, MongoDB Community Edition, Android Open Source Project);
341: [List Paragraph] self-hosted розгортанню на власній серверній інфраструктурі АТП або хмарному VPS (~$20–50/міс);
342: [List Paragraph] використанню смартфонів водіїв замість спеціалізованого бортового обладнання.
343: [Normal] Потенційна економічна ефективність: за оцінкою, впровадження підсистеми RoutePulse в АТП із 150 транспортними засобами дозволить скоротити витрати на паперовий документообіг (~15 хв/водія/зміну × 150 водіїв × 260 змін/рік × умовна вартість 1 хв), підвищити оперативність реагування диспетчера на інциденти (з ~10–15 хв при голосовому зв'язку до 1–2 хв при автоматичному сповіщенні), а також знизити відсоток несвоєчасно зафіксованих порушень розкладу.
344: [Normal] Ступінь готовності до реального використання: прототип є функціонально завершеним для базових сценаріїв роботи водія (авторизація, дорожній лист, GPS-трекінг, інциденти, карта маршруту). Для промислового впровадження необхідно: (1) розробити веб-кабінет диспетчера (не реалізовано у прототипі); (2) провести навантажувальне тестування при 150 одночасних підключеннях; (3) замінити cleartext-трафік (usesCleartextTraffic=true у manifest, необхідний для локальної розробки) на виключно HTTPS у продакшені; (4) налаштувати MongoDB Replica Set та автоматичне резервне копіювання; (5) пройти аудит безпеки перед розгортанням.
345: [Normal] Рекомендації щодо подальших досліджень та вдосконалень: розробка веб-клієнта диспетчерської служби (React або Vue.js + Leaflet); реалізація push-сповіщень FCM для оперативного сповіщення диспетчерів про критичні інциденти; впровадження аналітичного модуля (KPI-дашборд) на основі агрегаційних запитів MongoDB; розширення алгоритмів офлайн-синхронізації (конфлікт-резолюція при паралельному редагуванні); тестування на реальному автобусному парку для збору метрик продуктивності та юзабіліті.
