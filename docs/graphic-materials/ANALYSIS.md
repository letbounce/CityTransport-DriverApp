# Аналіз скрінів для дипломної роботи RoutePulse

## 1. Загальна оцінка

У папці **7 зображень**: 4 екрани Android-застосунку, 1 карта, 1 результат у MongoDB, 2 фрагменти коду сервера. Це добрий **мінімальний набір** для розділу «Графічні матеріали» і частини додатків, але **не повний** демонстраційний сценарій (немає активного рейсу, завершення рейсу, журналу інцидентів).

Якість скрінів: **достатня для звіту** — читабельний UI, видно українську локалізацію, реальні дані (маршрут 114, DRV-1042, КР-4412).

## 2. Покроковий аналіз кожного зображення

### G01 — Вхід.png → `G01-login-screen.png`

**Що показано:** екран `LoginScreen` — логотип RoutePulse, поля «ID водія» (`DRV-1042`) і «Пароль», кнопка «УВІЙТИ».

**Відповідність проекту:**
- FR-01 (авторизація), UC-01, компонент C1.
- Sequence-діаграма рис. 2.6 (Login → JWT).

**Що написати в поясненні (2–3 речення):**
> На рисунку Г.1 зображено початковий екран мобільного терміналу водія. Водій вводить ідентифікатор `DRV-NNNN` та пароль; після успішної перевірки на сервері (bcrypt + JWT) відбувається перехід до головного меню. Токен зберігається в EncryptedSharedPreferences.

**Заувага:** на скріні видно реальний device status bar — для звіту це нормально.

---

### G02 — Створення дорожнього листа.png → `G02-waybill-dashboard.png`

**Що показано:** `RouteDashboardScreen` — «Дорожні листи», користувач «Коксюк О.В.», блок «Новий дорожній лист»: вибір маршруту №114, ТЗ КР-4412 (електробус), список зупинок з плановим часом.

**Відповідність:**
- FR-02, FR-03; UC-02; sequence рис. 2.5 (створення waybill).
- Узгоджено з ER-моделлю (Route → Stop, Waybill).

**Сильні сторони для диплому:**
- Видно зв’язок **маршрут + ТЗ + розклад зупинок** в одному UI.
- Підпис «Маршрути та розклад зупинок збігаються з екраном «Мапа рейсів»» — аргумент **цілісності даних** між екранами.

**Що дописати в звіті:**
> Екран дозволяє обрати маршрут і бортовий номер транспортного засобу перед стартом рейсу; після підтвердження формується запис waybill зі статусом `in_progress` (див. рис. 2.5).

**Чого не вистачає на скріні:** кнопка «Отримати дорожній лист» / перехід на ActiveTrip — можна дозняти наступний кадр.

### G03 — Створення звіту про інцидент.png → `G03-incident-report.png`

**Що показано:** `IncidentReportScreen` — час 21:21, координати GPS (`50,53286, 30,61114`), «Чи можна рухатися самостійно?» = **Ні**, кнопки Галерея/Камера/Прибрати, «ВІДПРАВИТИ ЗВІТ».

**Відповідність:**
- FR-06; UC-05; алгоритм рис. 2.3; sequence рис. 2.7.

**Сильні сторони:**
- Демонструє **геоприв’язку** (кнопка «GPS зараз»).
- Демонструє **опційне фото** і бінарний атрибут `can_move_independently`.
- Відповідає полям `Incident.js`: `location`, `can_move_independently`, `photo_url`.

**Зауваги для покращення:**
- Не видно обраного **типу інциденту** і **зупинки** — якщо вони на екрані вище (прокрутка), зробіть **другий скрін з прокруткою вгору** або повний scroll.
- Не видно **опису** (description) — для алгоритму рис. 2.3 це обов’язкове поле; варто дозняти заповнену форму.

### G04 — Мапа маршруту.png → `G04-route-map.png`

**Що показано:** `TripMapRouteScreen` — «Автобус 114», карта OSM (Київ, Дніпро), синя лінія маршруту, зелені маркери зупинок, кнопки «Зупинки», «Оновити», «Моє GPS на маршруті».

**Відповідність:**
- FR-08; компонент C5 (OSMdroid + GeoJSON).
- Зовнішнє джерело: OpenStreetMap (на схемах 3.4, 3.7).

**Текст на карті:** «OpenStreetMap — дані маршруту з OSM (Overpass API) + телеметрія активних рейсів»; «Немає маркерів телеметрії для активних рейсів» — чесно показує стан **без активних рейсів інших водіїв** (нормально для демо).

**Пояснення для звіту:**
> Реалізовано перегляд маршруту на карті з використанням OSMdroid та тайлів OpenStreetMap. Зупинки відображаються маркерами вздовж лінії маршруту; функція live-телеметрії інших ТЗ передбачена API `/api/map/live-trips` (FR-10).

### G05 — waybill_completed.png → `G05-mongodb-waybill-completed.png`

**Що показано:** документ MongoDB: `driver_id: DRV-1042`, `route_number: 114`, `status: completed`, `started_at` / `completed_at`, `vehicle_id: KP-4412`, soft-delete поля `null`.

**Відповідність:**
- П. 3.4 «Результати реалізації», контрольний приклад.
- Даталогічна модель рис. 3.3, enum status waybill.

**Сильна сторона:** це **об’єктивне підтвердження** апробації (не лише UI).

**Пояснення:**
> Після сценарію «завершити рейс» у колекції waybills зафіксовано перехід статусу в `completed` з часовими мітками початку та завершення, що відповідає бізнес-логіці WaybillController.

**Рекомендація:** додати аналогічний скрін документа з колекції **incidents** після відправки звіту з Г.3.

---

### A01 — Waybill.png → `A01-code-waybill-schema.png`

**Що показано:** `server/models/Waybill.js` — поля driver_id, route_id (ref Route), status enum, timestamps, vehicle_id, soft-delete.

**Для додатку:** ілюстрація до п. 3.3, зв’язок код ↔ рис. 3.3 (даталогічна модель).

**Пояснення:** Mongoose-схема визначає обмеження `status` та посилання на маршрут; `timestamps` з полем `created_at`.

---

### A02 — Incident.png → `A02-code-incident-schema.png`

**Що показано:** `server/models/Incident.js` — type enum, location, photo_url, version_history[], is_modified, soft-delete.

**Для додатку:** підтверджує FR-07 (version_history) на рівні коду.

**Пояснення:** вбудований масив `version_history` зберігає snapshot попередніх версій звіту; коментар у коді про позначку «Змінений» узгоджений з UI редагування.

## 5. Готові абзаци для вставки в п. 3.4

> Апробацію підсистеми виконано на контрольному прикладі: авторизація водія DRV-1042, створення дорожнього листа для маршруту №114 на транспортному засобі КР-4412, реєстрація інциденту з GPS-координатами та завершення рейсу. Інтерфейс мобільного клієнта наведено на рисунках Г.1–Г.4; підтвердження збереження даних у центральній БД — на рисунку Г.5 (документ waybills зі статусом `completed`). Фрагменти серверних моделей Mongoose наведено в додатку (рис. А.1–А.2).
